# Автоматические тесты и капча: как пройти честно

Документ отвечает на вопрос, который обычно и стоит за запросом «нужен solver»:
**как сделать так, чтобы автотесты не падали на Cloudflare Turnstile, reCAPTCHA
v2/v3 и DataDome**. Правильный ответ — не обходить проверку, а сделать так,
чтобы в тестовом окружении её не было (или чтобы она всегда возвращала детерминированный результат). Все способы ниже — штатные механизмы самих
вендоров; они не ломаются после очередного обновления защиты, не требуют
поддержки и не создают юридический риск.

---

## 1. Cloudflare Turnstile: официальные тестовые ключи

Turnstile публикует dummy-ключи, которые работают на **любом** хосте, включая
`localhost`, и всегда дают детерминированный результат
([документация Cloudflare](https://developers.cloudflare.com/turnstile/troubleshooting/testing/)).

| Sitekey | Поведение | Виджет |
| --- | --- | --- |
| `1x00000000000000000000AA` | всегда проходит | visible |
| `2x00000000000000000000AB` | всегда блокирует | visible |
| `1x00000000000000000000BB` | всегда проходит | invisible |
| `2x00000000000000000000BB` | всегда блокирует | invisible |
| `3x00000000000000000000FF` | принудительно интерактивный челлендж | visible |

| Secret key (server-side `siteverify`) | Поведение |
| --- | --- |
| `1x0000000000000000000000000000000AA` | валидация всегда успешна |
| `2x0000000000000000000000000000000AA` | валидация всегда падает |
| `3x0000000000000000000000000000000AA` | «token already spent» (`timeout-or-duplicate`) |

Практические детали, на которых чаще всего ломают тесты:

* **Меняйте обе половины сразу.** Dummy-sitekey отдаёт фиктивный токен
  `XXXX.DUMMY.TOKEN.XXXX`, который **боевой** secret не примет; и наоборот —
  тестовый secret не примет реальный токен. Несовпадение пары даёт ошибку
  `bad-request`/`invalid-input-response`, и ищут баг не там.
* Тестовые ключи — это отдельный путь кода: подставляйте их через переменные
  окружения, а не правкой разметки.
* `3x00000000000000000000FF` нужен ровно для одного: проверить, что ваш layout
  с интерактивным виджетом не разваливается и submit разблокируется. Кликают
  по нему **рукой** в интерактивном тесте — или (обычно) не кликают вовсе,
  потому что в e2e-пайплайне этот кейс закрывается unit-тестом колбэка.
* Если нужны **ваши** ключи на локальной машине — добавьте `localhost` (или IP
  стенда) в allow-list хостов виджета в дашборде Turnstile. Тогда локальный
  тест получает настоящий токен легально.

```bash
# .env.test
TURNSTILE_SITEKEY=1x00000000000000000000AA
TURNSTILE_SECRET_KEY=1x0000000000000000000000000000000AA
```

### Если вы не контролируете ключи, но контролируете трафик

Cloudflare WAF позволяет правило **«Skip»** (или Custom Rule с action
`Skip`) для конкретного хоста/IP/заголовка — например, «для `Host:
staging.example.com` и заголовка `X-E2E: 1` не применять Managed Challenge».
Это точечное исключение на вашей зоне, а не обход чужой защиты.

## 2. reCAPTCHA v2/v3: тестовые ключи Google

Google публикует пару ключей, при которых виджет **не показывается**, а любая
серверная валидация проходит
([reCAPTCHA FAQ](https://developers.google.com/recaptcha/docs/faq)):

```text
Site key:   6LeIxAcTAAAAAJcZVRqyHh71UMIEGNQ_MXjiZKhI
Secret key: 6LeIxAcTAAAAAGG-vFI1TnRWxMZNFuojJ4WifJWe
```

Ограничения, которые надо знать:

* Пара относится к **v2** («No CAPTCHA» и «I'm not a robot»). Виджет в этом
  режиме печатает предупреждение «only for testing» — это нормально и, наоборот,
  полезно: сразу видно, что тестовый ключ не уехал в прод.
* Для **v3** отдельных «всегда-проходных» ключей нет; рекомендация Google —
  завести **отдельную пару ключей для тестового контура** и не полагаться на
  score (v3 оценивает трафик, на стенде score недостоверен). В коде теста
  проверяйте не `score >= 0.9`, а факт наличия/отсутствия токена и ответ бэкенда.
* В админке reCAPTCHA в список доменов добавьте `localhost` **и** `127.0.0.1`
  (это разные записи), иначе на стенде получите `invalid-input-site-key`.
* reCAPTCHA **Enterprise** вместо тестовых ключей имеет штатные *assessment
  exemptions* — освобождение по IP/по правилу. Это то, что настраивает владелец
  проекта, и это корректный путь для CI.

## 3. DataDome

DataDome — не капча, а скоринг-система, и «обхода» для автотестов у неё нет по
замыслу. Штатные механизмы (все — на стороне вашего аккаунта/админки):

1. **Whitelist rules** в дашборде: исключение по диапазону IP тестовых раннеров
   (CIDR), по хосту, по куке/заголовку, который проставляет ваш стенд.
2. **Тестовый стенд без тега DataDome** — самый дешёвый и самый честный вариант:
   protection включена на проде, на staging её нет вовсе (или включена в
   watch-only/monitor режиме, где решение не принимается).
3. **API-тесты** идут в обход web-защиты легально: у DataDome есть
   Validate-Request API для *вашего* бэкенда, а ваш транспортный тест может
   ходить прямо в origin в изолированном контуре.

Если вы не владелец свойства — единственный путь это не «обход», а
**разрешение**: переписка с security-командой сайта, участие в bug bounty с
явно прописанным scope, или тестовый стенд, который вам выдали.

## 4. Что делать в самом тесте

Паттерны, которые закрывают 95 % боли, — до всяких решалок:

* **`storageState` вместо логина в каждом тесте.** Один раз залогинились
  (в том числе через `arena_api.auth.verify.capture_storage_state`), сохранили
  файл, дальше `browser.new_context(storage_state=...)`. Логин-флоу проверяется
  ровно одним тестом, а не сотней.
* **Тестовый вход на бэкенде.** `POST /internal/test/login` → сессионная кука
  по секретному токену, доступному только в тестовом контуре. Дешевле и надёжнее
  любой автоматизации UI-логина; защита при этом остаётся включённой на проде.
* **Тестировать интеграцию виджета, а не виджет.** Проверяйте: токен положен в
  нужное поле с нужным `name`, кнопка submit заблокирована до токена, ответ
  бэкенда с `success:false` показывает ошибку, после ошибки виджет сделан
  `reset()` (токены одноразовые и живут ~5 минут). Это ровно те баги, которые
  ловятся в реальных проектах.
* **Не «решать», а матчить состояние.** В e2e достаточно
  `await expect(page.locator('input[name="cf-turnstile-response"]')).toHaveValue(/./)`
  — с тестовым sitekey это условие выполняется само.

## 5. Почему в `arena_api.auth` нет solvers

Модуль `arena_api/auth/` умеет всё, что связано с **жизнью** сессии, и не умеет
ничего, что связано с её **добычей хитростью**:

| Есть в библиотеке | Нет в библиотеке и не появится |
| --- | --- |
| `CookieJar`/`SessionStore`: хранение, атомарная запись, права `0600`, прунинг по expiry | Инъекция скриптов (`add_init_script`), подмена `navigator.webdriver`, `chrome.runtime` |
| `AutoSessionManager`: TTL, троттлинг, бэк-офф с джиттером, фоновый рефреш, `stats` | Подмена/рандомизация WebGL/Canvas/плагинов/языков/разрешения экрана/`permissions.query` |
| `HttpLivenessProbe`: живой ответ = «сессия годится», interstitial = «нужен человек» | Синтез и ротация User-Agent под «реальный браузер» |
| `ManualCheckpoint` / `PlaywrightCheckpoint`: открыть настоящий браузер, **дождаться человека**, прочитать куки, которые выставил сайт | Клик по чекбоксу Turnstile, перехват `cf_clearance`/`turnstileResponse`, audio-solver (Whisper/pydub) `reCAPTCHA` |

Причина не в сложности, а в цели. Все перечисленные техники существуют ровно
для одного: заставить чужую защиту пропустить трафик, который она явно не хочет
пропускать. Для «личного использования» это не меняет ни того, что нарушается
(`ToS`, а в ряде юрисдикций — Computer Fraud and Abuse Act / 18 U.S.C. § 1030 или
аналоги), ни того, что произойдёт с аккаунтом: бан по отпечатку, а не по IP.
Кроме того, это просто плохая инженерия для тестов: решалка, завязанная на
разметку чужого виджета и координаты чекбокса, ломается в среднем несколько раз
в месяц, и тогда тесты начинают «краснеть» по причинам, не связанным с вашим
кодом.

Практический эффект: тесты перестают зависеть от поведения защиты, потому что защита в тестовом контуре выключена конфигурацией,
а не обманута кодом.

## 6. Хранение сессий: чек-лист

Сессионные куки — это credential-эквивалент (владелец сессии = вы, до истечения
срока). Правила, которые реализует `SessionStore`:

* файл пишется во временный файл рядом + `os.replace` (нет полустёртого state
  после падения процесса), права `0600`, каталог `0700`;
* **не коммитить**: `.gitignore` для `**/session.json`, `**/storage_state*.json`;
  в CI — artifact с истечением срока, а не артефакт навсегда;
* ключ шифрования/`keyring` вместо файла — если файловая система общая;
* срок годности: `RefreshPolicy(cookie_ttl=..., expiry_margin=...)`, чтобы
  клиент не отправлял в запросе jar, который умер в полёте;
* отзыв: удаления файла мало, если токен живой — выход из сессии на стороне
  сервиса обязателен.
